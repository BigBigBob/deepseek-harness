### 一、项目技术架构
结论：当前项目采用的是“Cordis 插件微内核 + 事件溯源 Agent Runtime + 能力端口/适配器 + 多应用外壳”的架构，而不是传统的单体聊天应用。扩展性、可回放性和生命周期管理是核心设计目标，代价是包数量与运行时装配复杂度较高。

## 总体架构

```text
dsh CLI
  └─ Profile
      └─ Bundle / 用户 Patch 分层合并
          └─ Cordis Loader + Context
              ├─ Agent 核心运行时
              │   ├─ Session 事件日志
              │   ├─ System Prompt 组装
              │   ├─ LLM 路由
              │   └─ Tool 执行管线
              ├─ 能力插件
              │   ├─ FS / Shell / Subprocess / Sandbox
              │   ├─ Web / Skill / MCP
              │   ├─ Subagent / Workflow / Jobs
              │   └─ Approval / Permission / Credentials
              └─ 应用外壳
                  ├─ Web Host + Browser Client
                  ├─ Headless
                  ├─ SDK JSON-RPC
                  └─ ACP
```

### 1. 启动与装配层

唯一支持的 Node 应用入口是 `dsh`。CLI 只解析模式，然后动态加载 profile、插件管理或配置导出逻辑，见 [bin.ts](E:/code/agent/deepseek-harness/apps/cli/src/bin.ts:24)。

Profile 并不直接包含固定程序，而是按顺序叠加 Bundle patch、用户 patch 和命令行 overlay；最终由 Cordis Loader 创建插件树。实际创建 `Context`、加载 Loader、挂载根 Include 并执行激活审计的代码在 [app-boot](E:/code/agent/deepseek-harness/packages/boot/app-boot/src/index.ts:790)。

默认 `base` Bundle 已包含约 85 个插件行，包括模型、工具、会话、持久化、权限、沙箱、工作流和子 Agent；核心运行时最后由 `tools → system-prompt → agent-loop → llm-deepseek` 等行完成装配，见 [base/cordis.patch.yml](E:/code/agent/deepseek-harness/packages/bundle/base/cordis.patch.yml:471)。

这是一种运行时依赖注入架构：代码依赖服务接口，部署通过 YAML 决定使用哪个实现。

### 2. Agent 核心运行时

核心链路是：

```text
用户输入
 → Inbox
 → turn/start
 → System Prompt + Tool Schema
 → agent/pre-step
 → step/start
 → 从 Session 日志推导模型历史
 → LLM 流
 → assistant/message
 → Tool Calls
 → Tool Results
 → 下一 Step 或 turn/end
```

默认实现是 `ReactLoopAgent`，接口则单独位于 `dsh-agent`，因此 UI、Hook 和扩展插件不需要依赖具体循环实现。主要逻辑在：

- Agent 状态机与 Inbox：[agent.ts](E:/code/agent/deepseek-harness/packages/core/agent-loop/src/agent.ts:70)
- Turn 生命周期：[agent.ts](E:/code/agent/deepseek-harness/packages/core/agent-loop/src/agent.ts:258)
- 模型流与工具循环：[agent.ts](E:/code/agent/deepseek-harness/packages/core/agent-loop/src/agent.ts:344)
- 请求构造和模型路由：[agent.ts](E:/code/agent/deepseek-harness/packages/core/agent-loop/src/agent.ts:488)

`followup`、`steer`、`inject` 最终都进入两个持久化 Inbox 队列；取消通过 `AbortSignal` 向模型、工具和生命周期监听器传播。

### 3. 事件溯源的数据层

`Session` 是整个系统的事实来源。它保存追加式 `SessionEvent`，模型消息不是独立存储，而是通过 `deriveMessages()` 从日志重新推导，见 [Session](E:/code/agent/deepseek-harness/packages/core/session/src/index.ts:451) 和 [deriveMessages](E:/code/agent/deepseek-harness/packages/core/session/src/index.ts:820)。

这意味着：

- 模型看到的内容必须先进入日志；
- 恢复、Fork、转录、统计和 UI 投影都基于同一份事件；
- 工具调用、模型失败、取消、Turn/Step 边界都有持久记录；
- Session 格式升级使用相邻版本迁移，不覆盖已经发布的旧代文件。

持久化采用 `SessionPersistence → SessionHandle` 接口，默认是 JSONL/Zstandard 后端，并通过 flush checkpoint 保证模型请求和工具副作用前后的持久顺序，见 [persistence.md](E:/code/agent/deepseek-harness/docs/subsystems/persistence.md:91)。进程在 Turn 中途崩溃时，恢复层会追加合成的关闭事件，而不是截断历史，[恢复设计](E:/code/agent/deepseek-harness/docs/subsystems/persistence.md:95)。

### 4. 能力接口与策略管线

项目大量采用三段式能力接口：

```text
Service Definition → Provider → Consumer/Tool
```

例如：

- `llm`：模型接口、DeepSeek/Pi 等 Provider、Agent Loop Consumer；
- `fs`：文件系统接口、本地/E2B Provider、文件工具；
- `subprocess`：进程接口、本地实现、Shell/LSP/Terminal Consumer；
- `subagent`：调度接口、进程内或 SDK Provider、模型工具。

LLM 运行时统一管理 Provider 注册、模型发现、调用配置和流标准化，见 [LlmRuntime](E:/code/agent/deepseek-harness/packages/llm/llm/src/index.ts:330)。

工具则不是直接调用函数，而是经过：

```text
参数物化
 → tools/pre-execute
 → 单调安全 Guard
 → tools/execute
 → 工具实现
 → tools/post-execute
 → 输出校验、渲染和日志通知
```

对应代码在 [ToolRuntime.execute](E:/code/agent/deepseek-harness/packages/core/tools/src/index.ts:1333)。审批、权限、超时、沙箱和结果修剪都可以作为管线包装器插入，而无需修改 Agent Loop。

### 5. Web、SDK 与其他应用面

Web 采用明确的 Host/Client 双平面：

- Host：Node HTTP 服务、Session/Workspace Controller、Typert Gateway；
- Client：独立 Cordis 插件树、模块加载器、Connection、React Slot UI；
- UI 功能不是集中式组件树，而是多个 `ui-*` 插件向类型化 Slot 注册内容。

浏览器端自己创建 Cordis `Context`，按照 Host 注入的 `__DSH_BOOT__` 模块图加载插件，见 [client boot](E:/code/agent/deepseek-harness/packages/client/web/src/boot.ts:22)。

普通业务调用采用 Typert 生成的类型化 Remote API。调用路径是：

```text
Client remotes → Gateway → Connection → WebServer → Host Service
```

Typert 在 Host 构建阶段分析装饰器和类型，生成 Host 描述符、Zod 校验器和 Client API；因此 Host 构建必须先于 Client 构建，见 [api-gateway.md](E:/code/agent/deepseek-harness/docs/api-gateway.md:95)。Remote 主要服务一问一答式调用，Session 流和下载等数据使用单独协议，[边界说明](E:/code/agent/deepseek-harness/docs/api-gateway.md:158)。

SDK 和 ACP 没有另起一套 Agent 内核：它们也是 profile。TypeScript/Python SDK 通过 stdio JSON-RPC 启动同一个 `dsh --profile sdk` Runtime。

### 6. 工程与构建架构

当前仓库规模约为：

- 262 个 `packages/*/*/package.json`；
- 50 个包分组；
- 45 个浏览器 Client 包；
- 约 1,257 个 `spec/e2e` 测试源文件。

主要技术栈是 TypeScript ESM、Node `^22.19 || >=24`、pnpm workspace、Vitest、tsdown、Vite、Zod/Schemastery。Host 和 Client 使用不同 TypeScript Project Reference 图，并按 Host → Client → Web 顺序构建，[package.json](E:/code/agent/deepseek-harness/package.json:22)。

另外还有：

- `python/`：SDK 与捆绑 Runtime；
- `native/landlock-run/`：Linux Landlock 原生沙箱启动器；
- `vendor/`：固定版本的 Cordis 源码；
- `scripts/`：大量架构、依赖、文档和发布门禁。

## 架构评价

主要优点：

- 插件、Provider、Agent Loop 都可以替换，扩展通常不需要修改核心循环。
- 事件日志让模型上下文、恢复、审计和 UI 投影具有同一事实来源。
- `ctx.effect()` 和 disposer 使插件卸载、Agent 销毁和资源回收有明确所有权。
- Host/Client、源码/构建产物、接口/实现之间的边界比较严格。
- 权限、审批、沙箱、超时和凭据不是散落在工具实现中，而是独立策略层。

主要成本与风险：

- 262 个包、85 个基础插件行带来了较高的导航、依赖和配置理解成本。
- 很多关系在运行时通过 `ctx` 服务和事件建立，单看静态 import 图不足以理解系统。
- waterfall 监听器必须正确调用 `next()`，错误实现可能短路整个策略链。
- Typert 生成物使 Host/Client 类型安全较强，但开发时容易遇到生成物过期或构建顺序问题。
- Session 事件属于兼容性核心；新增模型可见信息往往会连带影响事件类型、持久化、迁移、两套 SDK 和快照。
- 发现一处轻微文档漂移：实际存在 [packages/mcp](E:/code/agent/deepseek-harness/packages/mcp/README.md:6)，但顶层 [package group 表](E:/code/agent/deepseek-harness/packages/README.md:25) 尚未列出该组。

总体上，这是一个架构纪律很强、面向长期演进的 Agent 平台；它更接近“可配置的 Agent 操作系统/运行时”，而不是单一 DeepSeek 客户端。本轮为只读分析，没有修改文件或运行测试。
