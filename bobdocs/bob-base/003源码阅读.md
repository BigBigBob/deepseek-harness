- Everything is a plugin：模型、工具、Session、Agent Loop 都是插件。

结论：先把 DeepSeek Harness 看成四层，而不是一条写死的调用链。

| 层 | 回答的问题 | 本轮看到的内容 |

## 一条简化调用链


## 1. `docs/cordis-primer.zh.md`：先学协作规则

为什么读：它定义 Cordis 插件之间怎么找到彼此、怎么参与生命周期。核心内容在[五个核心概念](E:/code/agent/deepseek-harness/docs/cordis-primer.zh.md:7)。

第一次出现的术语可以这样理解：

- **Cordis**：插件运行时。它把插件挂入上下文，并管理启动、reload 和 teardown。
- **service**：放在稳定 `ctx` 键上的能力，例如 `ctx.tools`、`ctx.llm`、`ctx.sessions`。调用方依赖这个公开能力，不直接 `new` 某个具体实现。[`ctx.<key>`](E:/code/agent/deepseek-harness/docs/cordis-primer.zh.md:10)
- **inject**：依赖注入声明。插件声明“我需要 `headlessStartup`”，Cordis 等该 service 就绪后再启动它；这取代了手工安排插件启动顺序。[`inject`](E:/code/agent/deepseek-harness/docs/cordis-primer.zh.md:11)
- **effect**：受插件生命周期管理的注册操作。`ctx.effect()` 或 `ctx.on()` 安装的东西会在插件卸载时撤销；返回的清理函数称为 disposer。[`ctx.effect()`](E:/code/agent/deepseek-harness/docs/cordis-primer.zh.md:13)
- **waterfall**：一串可包裹结果的监听器。每个监听器必须调用 `next()` 才会继续下游；直接返回会短路。[`ctx.waterfall`](E:/code/agent/deepseek-harness/docs/cordis-primer.zh.md:33)

输入、输出和运行时关系：

- 它是说明文档，不接收运行时输入，也不注册 service 或事件。
- 它说明工具扩展归 `ctx.tools`、模型流归 `ctx.llm`、实时 Agent 协调归 `ctx.agents`。[实践规则](E:/code/agent/deepseek-harness/docs/cordis-primer.zh.md:47)
- 它没有对应的逐页运行时单测；主要受链接、双语配对和文档结构检查保护。这里的行为仍要由具体包测试证明。

## 2. `docs/architecture.zh.md`：把包放到请求路径上

为什么读：它把 Composition、Contract、Implementation 和 Durable state 连起来，但不会提供具体函数体。

Composition：

- Profile 是具名组装，bundle 是可分发的配置层。
- 层叠顺序是：bundle 列表 → profile patch → home patch → `--patch` overlay。
- patch 按 `id` 找已有行并替换其整个 `config`，或者插入新行。[Profile 与组合包](E:/code/agent/deepseek-harness/docs/architecture.zh.md:15)

Contract：

- `core/session` → `ctx.sessions`
- `core/tools` → `ctx.tools`
- `core/agent` → `Agent`、`ctx.agents`、`agent/*`
- `core/agent-loop` → `ctx.agentLoop`
- `llm/llm` → `ctx.llm`

这些是其他包可以依赖的公开协作点，而不是具体实现类。[核心包表](E:/code/agent/deepseek-harness/docs/architecture.zh.md:49)

这里还出现了 **seam**：一项可替换能力，由接口定义、实现提供方、能力消费者三部分组成。例如 `llm/llm` 定义模型能力，而具体模型 adapter 是可替换提供方。[能力 seam](E:/code/agent/deepseek-harness/docs/architecture.zh.md:119)

Implementation 的最小模型：

- **turn（轮次）**：从领取输入开始，到没有待处理工作为止；允许包含零个或多个 step。
- **step（步骤）**：一次模型请求，加上该响应产生的工具调用。
- 第一条输入若被 `agent/pre-step` 拒绝，仍会留下一个零 step 的持久 turn。[轮次流程](E:/code/agent/deepseek-harness/docs/architecture.zh.md:78)

Durable state：

**SessionEvent** 是追加进 Session 日志、可以在重启后重放的类型化事实。这里采用的是事件溯源：不只保存“当前对话对象”，而是保存依次发生的事实，再由 `deriveMessages()` 投影出模型历史。

持久事件包括：

- `turn/start`、`turn/end`
- `step/start`、`step/end`
- `user/message`
- `assistant/message`、`assistant/attempt`
- `tool/call`、`tool/result`
- 条件产生的 `request/header`

`agent/request`、`llm/stream`、`tools/execute`、`agent/assistant-stream` 等是实时扩展事件，并不因此自动成为 SessionEvent。[会话日志](E:/code/agent/deepseek-harness/docs/architecture.zh.md:109)

关键原则是“模型可见即已记录”：模型看到的内容必须能从 Session 日志重建；新增模型可见输入通常需要扩展 `SessionEventMap`。[`SessionEventMap`](E:/code/agent/deepseek-harness/docs/architecture.zh.md:115)

## 上轮检查题答案

1. `inject: [headlessStartup]` 表达真实依赖关系：Cordis 只在 service 存在时激活 runner；YAML 文本顺序只是配置排列，不能保证依赖已经就绪。它也让卸载、重载时的生命周期跟随 service。

2. `tools/execute` 是实时 waterfall 事件，只参与当前进程的工具流水线；`tool/result` 是持久 `SessionEvent`，会追加到 Session 日志。

3. 模型调用工具后，工具结果通常要再次送给模型，因此一个 turn 可以有多个 step。若首批输入被 `agent/pre-step` 拒绝或改为空，turn 仍记录开始和结束，但可以没有 step。

# 第二轮：CLI 参数如何变成 headless task

这一轮最重要的结论是：

> CLI 启动器不理解“task”；它只把剩余参数发布成通用 `cmdlineArgs` service。`headless-startup` 插件才把这些参数解释为 task，并发布第二个 service：`headlessStartup`。

## 简化调用链

```text
process.argv.slice(2)
→ parseDshArgs(...)
→ invocation.mode === "profile"
→ runProfile({ environment, profile, patchFiles, args })
→ composeProfile()
→ boot(...全部 patch...)
→ provideCmdline(hostCtx, { args, exit, ready })
→ ctx.cmdlineArgs 就绪
→ Cordis 激活 headless-startup
→ apply(ctx)
→ parseCmdline(ctx, Commander)
→ ctx.provide("headlessStartup", { task })
→ Cordis 才能激活 headless-runner
```

截至本轮，task 仍只是启动期 service 值，还没有成为 Session 日志里的持久事实。

当结果是 profile 模式时，它动态导入并调用 [`runProfile`](E:/code/agent/deepseek-harness/apps/cli/src/bin.ts:26)，传入：

- `profile`: 如 `headless`；
- `patchFiles`: 所有 `--patch`；

它没有 `ctx` 依赖。末尾的 `invocation satisfies never` 是 TypeScript 穷尽检查：将来新增 invocation 类型却忘记补 switch 分支时，编译会失败。

# 第三轮

## 上轮检查题答案

1. `startup.ts` 不直接读 `process.argv`，是为了分离职责：launcher 负责取得并冻结参数，应用插件负责解释参数。这样 Profile 启动保持通用，参数可跨 reload 保持，也便于测试注入。

## 上一轮理解检查题答案

1. 为什么 `AgentRegistry.create()` 不直接 `new Agent`？

`AgentRegistry` 属于公共接口层，只负责提供稳定入口；具体怎样创建 Session、选择驱动器、管理生命周期，由 `AgentFactory` 决定。

`AgentRegistry.create()` 实际把调用转给当前注册的 `factory.createAgent()`，见 [`AgentRegistry.create` (line 400)](E:/code/agent/deepseek-harness/packages/core/agent/src/index.ts:400)。默认工厂由 `AgentLoop` 通过 [`AgentRegistry.setFactory` (line 367)](E:/code/agent/deepseek-harness/packages/core/agent/src/index.ts:367) 注册。

所以：

```
Contract: AgentRegistry.create()
    ↓ 委托
Implementation: AgentLoop.createAgent()
    ↓ 构造
ReactLoopAgent
```

这样其他驱动器可以替换 AgentLoop，而 headless 无须改变。

1. 为什么在第一次 `whenIdle()` 后才记录 `firstSeq`？

[`runHeadless` (line 184)](E:/code/agent/deepseek-harness/packages/bundle/headless/src/index.ts:184) 创建 Agent 后先等待它空闲，再记录：

```
await agent.whenIdle()
const firstSeq = agent.session.seq
```

这把 Session 划成两个区间：

- `firstSeq` 之前：创建、setup、`agent/session-start` 插件可能产生的初始化事实；
- `firstSeq` 之后：本次 headless task 独占的运行结果。

[`summarize` (line 64)](E:/code/agent/deepseek-harness/packages/bundle/headless/src/index.ts:64) 只扫描后一个区间，因此不会把启动阶段的 assistant 输出误认为本次任务答案。

1. reasoning、最终答案和 

   ```
   flush()
   ```

1. 为什么 `user/message` 必须在 `session.deriveMessages()` 之前追加？

因为 `deriveMessages()` 是从 Session 日志重建模型历史。若先推导再记录：

```
→ session.deriveMessages()
→ 构造模型请求
```

1. 注册 Agent 工厂和发布具体 Agent 有什么区别？
   - 注册工厂是 Composition 行为：[`AgentLoop.constructor` (line 383)](E:/code/agent/deepseek-harness/packages/core/agent-loop/src/index.ts:383) 把一个长期存在的“Agent 创建能力”安装到 `ctx.agents`。


1. 为什么先写 `assistant/message` 再执行工具？

因为工具调用指令本身来自模型回复。必须先把这份原始模型决定记录下来，才能：

- 证明工具为什么被调用；

```

→ tool/call
→ tool/result
```

### 并发不是“全部 Promise.all”

调度器把调用分成两种模式：

- `parallel`：工具 body 可以在并发上限内重叠执行；
- `exclusive`：形成屏障，前面的并行组必须完全结束后才能启动。

见 [`executeToolCalls` (line 83)](E:/code/agent/deepseek-harness/packages/core/agent-loop/src/tool-calls.ts:83) 和 [`runGroup` (line 122)](E:/code/agent/deepseek-harness/packages/core/agent-loop/src/tool-calls.ts:122)。

未启动的调用会在真正启动前重新读取 `executionMode()`。因此工具注册或策略在运行中变化时，后续调用可能从 parallel 变成 exclusive。

### 执行可以乱序，提交必须按模型顺序

工具 body 可以并发完成，但 [`commitReady` (line 147)](E:/code/agent/deepseek-harness/packages/core/agent-loop/src/tool-calls.ts:147) 只提交连续、按模型顺序就绪的结果。

例如模型输出 A、B：

```
实际完成：B → A
Session 提交：tool/result A → tool/result B
```

这样下一次 `session.deriveMessages()` 看到的工具结果顺序始终与模型 tool-call 顺序一致。

### additionalContexts 和 concludesTurn

每个结果提交后：

1. 先追加 `tool/result`；
2. 再把 `additionalContexts` 交给 `acceptContext()`；
3. AgentLoop 把它们放入 `next-step` Inbox；
4. 下一步再记录为 `user/message`。

见 [`commitReady` (line 152)](E:/code/agent/deepseek-harness/packages/core/agent-loop/src/tool-calls.ts:152)。

`concludesTurn` 表示工具建议结束当前 turn，但它不能丢弃已经存在的 additional context 或并发到达的 steering；有待处理 `next-step` 输入时，AgentLoop仍会继续一步。

## 上一轮理解检查题答案

1. 为什么 `prepareCall()` 要固定模型配置和 adapter generation？

因为 `request/header` 记录的必须与真正执行请求的 adapter 完全一致。若 prepare 后发生热重载，再从 registry 查一次，可能组合成“旧 adapter 的模型能力 + 新 adapter 的网络实现”。

[`LlmRuntime.prepareCall` (line 904)](E:/code/agent/deepseek-harness/packages/llm/llm/src/index.ts:904) 因此返回只能使用一次的 `PreparedLlmCall`，同时固定：

- 最终 config；
- context window；
- retry policy；
- adapter 默认值；
- 实际 stream 函数。

1. 并行工具 B 先完成时，为什么仍先写 `tool/result A`？

模型按 A、B 的顺序发出调用，下一次模型请求也必须按这个顺序看到结果。否则并发时序会改变对话语义，并让相同 Session 无法稳定重放。

[`commitReady` (line 147)](E:/code/agent/deepseek-harness/packages/core/agent-loop/src/tool-calls.ts:147) 只从当前最前面的未提交 slot 连续提交。因此 body 可以按 B→A 完成，日志仍按 A→B 写入。

1. 非法 JSON 参数怎样处理？真正校验在哪里？

[`parseArguments` (line 104)](E:/code/agent/deepseek-harness/packages/core/agent-loop/src/tool-calls.ts:104) 不报错，而是保留原始字符串：

```
空字符串   → {}
合法 JSON  → 解析值
非法 JSON  → 原始字符串
```

对于 `defineTool()` 创建的工具，真正的 schema 校验在其生成的 `execute` 包装器中，见 [`defineTool` (line 545)](E:/code/agent/deepseek-harness/packages/core/tools/src/schema.ts:545)；违反 schema 时抛出 `ToolArgsError(INVALID_ARGS)`，随后被 ToolRuntime 规范化为普通错误结果。

但直接注册的原始 `ToolDefinition` 不会自动获得这层参数校验，必须由工具自身验证。

## 4. Implementation：一次工具调用经过哪些阶段

### 参数实体化

[`createExecution` (line 1355)](E:/code/agent/deepseek-harness/packages/core/tools/src/index.ts:1355) 首先：

- 分配不可伪造的 execution token；
- 补全 root call id；
- 将参数复制成 lossless JSON；
- deep-freeze 参数；
- 创建 `deferContext()` 和 `concludeTurn()`。

这里校验的是“能否无损表示为 JSON”，不是工具参数 schema。

### Pre-execute、approval、guards

[`prepareExecution` (line 1454)](E:/code/agent/deepseek-harness/packages/core/tools/src/index.ts:1454) 的顺序是：

```
tools/pre-execute waterfall
→ ask 时查询 approval
→ monotonic guards
```

`PreToolDecision` 可以是：

```
allow
deny(reason)
ask(reason?)
```

guard 是“单调拒绝”：

- 返回字符串：拒绝；
- 返回 `undefined`：不干预；
- 没有 allow 能力。

因此即使后注册的 pre-execute listener 强制返回 allow，也无法推翻 guard 的拒绝。这让所有者的安全策略不依赖 listener 排序。

### Execute

[`dispatchScheduledExecution` (line 1560)](E:/code/agent/deepseek-harness/packages/core/tools/src/index.ts:1560) 主持 `tools/execute` waterfall。监听器调用 `next()` 才进入 [`dispatchToolBody` (line 1523)](E:/code/agent/deepseek-harness/packages/core/tools/src/index.ts:1523)。

- 再次按 Agent scope 查找工具；
- 调用 `ToolDefinition.execute()`；
- 将异常转换成 `ToolExecutionFailure`；
- 等待已启动的工具真正收敛。

`tools/execute` wrapper 可以临时替换 signal，但 ToolRuntime 会把原始 caller signal 重新融合进去，不能借此摆脱取消。

### 输出检查和 Post-execute

工具 body 成功后，[`createSuccessResult` (line 1784)](E:/code/agent/deepseek-harness/packages/core/tools/src/index.ts:1784) 依次执行：

## 5. 最容易混淆的两个“result”

```
tools/result   → 实时 Cordis 事件，复数 tools
tool/result    → 持久 SessionEvent，单数 tool
```

准确顺序是：

```
tools/result live event
→ ToolRuntime.execute 返回
→ AgentLoop append('tool/result')
```

ToolRuntime 不依赖 Session，也不直接写普通 `tool/call` 或 `tool/result`。这是因为 ToolRuntime 也允许没有 Agent 的独立调用；只有 AgentLoop 知道当前 turn、step 和应该写入哪个 Session。

Durable `tool/result` 保留：

- 模型可见 `content`；
- `isError`；
- 结构化错误信息；
- UI `meta`。

它不保留：

- 内部规范 `value`；
- `additionalContexts`；
- `concludesTurn`；
- pre/post policy 的具体决策过程。

additional contexts 会通过 Inbox 另行持久化，并在下一 step 成为 `user/message`；`concludesTurn` 的最终效果体现在是否出现下一 step 以及 `turn/end`。

2. `tools/result` 与 `tool/result` 有什么区别，谁先发生？

   顺序是：

   ```
   工具结果最终化
   ```

   ToolRuntime 可以脱离 Agent 使用，输入中的 `agent` 本来就是可选的；它也不知道当前 `turn`、`step`、Session 和模型调用顺序。[`ToolExecutionInput` (line 307)](E:/code/agent/deepseek-harness/packages/core/tools/src/index.ts:307)

# 第七轮：Session 日志、surface 与 flush

> `Session` 保存“发生过什么”的仅追加日志；surface 从日志中计算“下一次模型现在能看到什么”；`SessionStore` 管理生命周期和持久化检查点，但自己不写磁盘。

## 四、Implementation：事件怎样进入日志

[`Session.append` (line 699)](E:/code/agent/deepseek-harness/packages/core/session/src/index.ts:699) 的顺序非常关键：

1. 把 `data` 和 surface 元数据复制成无损 JSON 快照。
2. 用当前 `log.length` 分配 `seq`，加入 `Date.now()` 并深度冻结。
3. 调用 [`SurfaceManager.validateNext` (line 440)](E:/code/agent/deepseek-harness/packages/core/session/src/surface.ts:440)，在日志变化前验证 surface 操作。
4. 对 live Session，先解析 `session/event` 的监听器；内部 dispatch 校验可以在提交前拒绝。
5. `this.log.push(event)`——这是内存提交点。[`Session.append` (line 737)](E:/code/agent/deepseek-harness/packages/core/session/src/index.ts:737)
6. 提交后发布实时 `session/event`；普通观察者抛错只记录警告，不能撤销事件。[`invokeContainedSessionObservers` (line 408)](E:/code/agent/deepseek-harness/packages/core/session/src/index.ts:408)

因此：

```
append 成功
≠ 已经写盘
= 不可变事件已经进入内存日志，并已交给持久化观察者
```

## 五、surface 怎样变回模型消息

surface 是“当前模型可见的事件顺序”，并不是另一份日志。只有三种事件能进入它：

- `user/message`
- `assistant/message`
- `tool/result`

[`deriveEventMessage` (line 90)](E:/code/agent/deepseek-harness/packages/core/session/src/surface.ts:90) 的规则是：

- user event → 原样返回 user message；

## 六、flush 到底保证什么

[`SessionStore.flush` (line 1117)](E:/code/agent/deepseek-harness/packages/core/session/src/index.ts:1117)：

- 找到该 live Session 的 scope；
- 并行启动所有 `session/flush` 监听器；
- 等全部监听器结束；
- 若有失败，等其他监听器也结束后再抛出第一个失败；
- 返回是否至少有一个监听器参与。

所以：

- 返回 `true`：至少有一个持久化参与者，并且所有参与者成功完成。
- 返回 `false`：没有监听器；调用本身成功，但不能据此声称写盘完成。
- 抛错：某个持久化参与者失败。

headless 在 `whenIdle()` 后先 `await sessions.flush()`，再扫描 Session 日志、输出最后的 assistant 文本并决定退出码。[`summarize` (line 64)](E:/code/agent/deepseek-harness/packages/bundle/headless/src/index.ts:64)、[`run` (line 205)](E:/code/agent/deepseek-harness/packages/bundle/headless/src/index.ts:205)
